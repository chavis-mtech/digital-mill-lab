# Demo Database Data Dictionary

## สรุปภาษาไทย

เอกสารนี้อธิบายตารางและฟิลด์หลักของฐานข้อมูลสาธิต (SQLite เป็นค่าเริ่มต้น และรองรับ PostgreSQL) รวมถึงหน่วย ที่มาของข้อมูล ชุดข้อมูลสังเคราะห์ตามสถานการณ์ การแยกข้อมูลตามเซสชัน และข้อมูลที่ไม่เปิดเผยผ่าน API รายชื่อคอลัมน์ในเอกสารนี้อ้างอิงจาก schema ที่สร้างอัตโนมัติ ไม่ได้เป็นข้อมูลของบริษัทจริง

## What the database is

The demo database holds **synthetic data** for a **fictional** company and mill: "Demo Palm Oil Co. (fictional)" and "Demo Palm Mill A". It is generated by a deterministic, seeded process. It covers 120 days of data ending at the demo anchor date. It is not connected to any real system, and nothing in it is company data. Public parameters are used only as ranges and assumptions. [Synthetic Demonstration Data]

The schema has 44 tables, grouped into the domains below. The schema itself is generated from the SQLAlchemy models. Do not hand-edit it. Alembic migration `0001` creates the same schema.

## Conventions used in every table

- **Time.** All timestamps are stored in UTC. The mill business day is `Asia/Bangkok`. The facility `timezone` column defaults to `Asia/Bangkok`.
- **Provenance (`data_kind`).** Most tables have a `data_kind` column. The defaults in the schema are `synthetic`, `synthetic_actual`, `forecast`, `what_if` and `sample_document`. The per-table defaults are listed below.
- **Units.** Mass is in tonnes (`_t`) or kilograms (`_kg`), as the column name says. Energy is in kWh, steam in tonnes, water in m3, and diesel in litres. Percentages are stored as numbers in percent, for example `oer_pct` = 18.2.
- **Session scope (ADR-006).** Ten tables are scoped to a visitor's demo session. A `session_id` that is NULL marks the shared seeded baseline. Visitors' writes are isolated by `session_id`.
- **Private table.** `injected_events` is never exposed through the API. It holds ground-truth labels for anomaly injection and is used only by ML evaluation.

## Session-scoped tables

These tables have a `session_id` column. A NULL value means the seeded baseline:

`alert_status_changes`, `anomaly_status_changes`, `audit_logs`, `business_scenarios`, `copilot_messages`, `copilot_sessions`, `maintenance_events`, `recommendation_decisions`, `work_order_status_history`, `work_orders`.

## Provenance: how to read `data_kind`

- `synthetic_actual`: a value up to the selected `as_of` date, produced by the synthetic generator. Used on the operational fact tables.
- `forecast`: a model output (`ai_predictions`).
- `what_if`: a scenario result (`business_scenarios`).
- `synthetic`: used on reference and dimension tables such as `companies`, `equipment`, `sensors` and `prices`. It marks synthetic reference data.
- `sample_document`: a knowledge-base sample document (`kb_documents`).

The API must attach a provenance object with `kind`, `source`, `as_of` and `model_version` to every numeric result. See the KPI guide.

## Known differences between the KPI definitions and this schema

The KPI definitions use some logical names that are not tables or columns in the current schema. When you build or read a number from the database, use the schema names below.

1. **Logical entities without a table.** The KPI definitions list `cpo_dispatch`, `cpo_tank_reading`, `ramp_stock_reading`, `equipment_state_event`, `cost_item` and `energy_reading`. None of these is a table in the current schema. Dispatch and tank readings are not stored as separate tables. Ramp stock is not stored as a reading table. Equipment state and cost items are not stored as event tables.
2. **Lab results.** The KPI definitions call the lab table `lab_result`. The schema table is `quality_measurements`.
3. **Energy fields.** The KPI definitions use `kwh_generated` and `kwh_import`. The schema uses `self_generated_kwh` and `grid_import_kwh`, and `electricity_kwh` for total use.
4. **Queue events.** The KPI definitions use `truck_id`. The schema uses `truck_trip_id` on `queue_events`.
5. **Weighbridge deduction.** The KPI definitions show `deduction_kg` on the weighbridge ticket. The schema has no such column. The deduction is `deduction_pct` on `ffb_deliveries`.
6. **Alert statuses.** The KPI definitions count alerts whose status is `open`, `acknowledged` or `in_review`. The schema allows `new`, `acknowledged`, `in_progress`, `resolved` and `dismissed`. The values `open` and `in_review` are not valid alert statuses in the schema.
7. **Alert timestamps.** The KPI definitions use `opened_at`. The schema uses `raised_at` and `resolved_at`.
8. **Downtime reason codes.** The KPI definitions split downtime into planned, unplanned, starved and other reason codes. The schema has `downtime_min` on `process_hourly`, `production_shifts` and `maintenance_events`, and a `planned` boolean on `maintenance_events` only. No reason-code column exists on the hourly or shift tables. A starved-versus-breakdown split cannot be read directly from the schema without an added field.
9. **Provenance values.** The provenance set in the build plan is `synthetic_actual`, `forecast` and `what_if`. Several reference tables default to `synthetic`, which is outside that set. Treat `synthetic` as reference metadata and keep it out of numeric KPI provenance.

These differences are for the team to resolve. This sample dictionary does not change the schema.

## Limits of this document

- This is a sample dictionary for the demo. It describes the schema as generated, and column names may change if the schema changes. The generated schema doc is the authority.
- The dictionary lists the key columns of each table, not every column. For a full column list, check the generated schema.
- The data is synthetic for a fictional company. Nothing here describes a real company system or record.
- Constraints shown here (for example value ranges) are the ones in the schema at the time of review. Some checks are enforced by the database. Others are enforced by application code.
